# 系统设计文档

本版完成基于MySQL的家政预约核心闭环，采用前后端分离和三层架构。核心业务在auth-service中形成模块化单服务；保留其他Spring Cloud模块作为后续拆分骨架。

## 分层

React页面 → api.js HTTP适配 → AuthController/OrderController → AuthService/OrderService → UserStoreService/OrderRepository → JdbcTemplate → MySQL。

SessionService将Bearer令牌摘要映射为用户，所有订单角色与归属判断在后端执行。前端路由仅用于交互引导。密码使用BCrypt强度12，旧SHA-256在成功登录后升级，不再接受明文。

## 订单与一致性

主路径：待支付→待派单→已派单→已接单→服务中→已完成→已评价；在线人员也可从待派单直接接单。开始必须已接单，完工必须服务中。只有未支付可取消，派单前可改约。售后申请是独立标记，审批待实现。

订单动作在@Transactional中执行，先锁订单记录，再锁相关人员映射/档案。支付记录每单唯一，已支付请求幂等；派单/接单检查状态，冲突返回409。订单版本每次变更递增，客户端可传version检查陈旧操作。业务状态、人员状态、支付记录和操作审计同事务提交。

## 数据结构

原七表保留，新增auth_sessions、provider_accounts、order_events。orders扩展联系人、版本、取消与售后字段。新增订单用户/人员状态索引，支付order_id唯一约束及核心关系外键。`sql/install.sql`用于空库；`sql/upgrade_v2.sql`为已有库一次性升级。

## 前端

服务器订单为权威数据源；每次动作成功后重新获取快照，并每5秒轮询。会话令牌仅存sessionStorage，不保存密码；清除旧localStorage演示数据。应用启动先验证/me，再开放受保护路由。请求失败显示提示，不生成本地成功结果。

## 边界

模拟支付不扣款。退款/投诉仅申请持久化；库存为样例。监控页实际调用快照展示可用性与一次请求耗时，不展示伪造吞吐率。未实现分布式治理、真实支付、技能与时段匹配、分页、生产压测。单库事务可保证本版一致性，拆服务时需重新设计事件与补偿。
